### Wikidata

暂不下载全站 dump。Wikidata 全站规模巨大，而本项目只需要带出生日期的人物及少量属性；直接下载全量 dump 会增加存储、解析和版本管理成本。

第一版采用按月或按年分批的 SPARQL 抽取：

```text
data/raw/wikidata/2026-07-31/1900-01.jsonl
data/raw/wikidata/2026-07-31/1900-02.jsonl
...
data/raw/wikidata/2026-07-31/manifest.json
```

每个批次必须保存：查询文本、查询时间、返回条数、HTTP 响应哈希和日期范围。只有明确需要本地重跑全量解析时，才考虑下载官方 dump。

## 推荐的四层存储

```text
data/
├── raw/                 # 上游原始归档，只读，不修改
│   ├── adb/<release>/
│   ├── cbdb/<release>/
│   └── wikidata/<snapshot>/
├── staging/             # 解压、格式转换后的中间文件
│   ├── adb/*.jsonl
│   ├── cbdb/*.parquet
│   └── wikidata/*.jsonl
├── numerology.db        # 规范化后的唯一事实库
└── features/            # 分析宽表，Parquet，每个流派/配置一份
    ├── ziping.parquet
    ├── ditiansui.parquet
    └── qiongtong.parquet
```

`data/` 已被 `.gitignore` 忽略，原始数据库不进入 Git。代码、schema、导入脚本和每个数据快照的 manifest 进入 Git。

## 不建议直接把三个数据库合并成一张人物表

第一原则是：不同来源的原始人物记录不自动去重。

原因：

- ADB、Wikidata、CBDB 的人物覆盖范围和身份粒度不同；
- 同名不代表同一个人；
- 日期、地点和职业定义不同；
- 误合并会制造比重复记录更严重的数据错误。

建议在规范化库中使用以下关系：

```text
sources
  └── source_snapshots
        └── source_records
              └── persons

persons
  ├── birth_facts
  ├── occupations
  ├── life_events
  └── chart_variants
```

### 建议的核心字段

`source_snapshots`：

```text
snapshot_id
source
release_name
retrieved_at
source_url
license
raw_path
sha256
record_count
```

`source_records`：

```text
source_record_id
snapshot_id
source_id
raw_payload_path
raw_payload_hash
```

`persons` 只保存跨来源稳定的内部 ID 和最小身份字段；来源特有字段放在 `birth_facts`、`occupations`、`life_events` 等表中。

`birth_facts` 必须保留不确定性：

```text
birth_date_start
birth_date_end
date_precision
birth_time
time_precision
timezone_meridian
latitude
longitude
source_record_id
```

例如只有年份的出生日期，保存为 `[YYYY-01-01, YYYY-12-31]`，不能伪造为 `YYYY-01-01`。

## 三个数据库的落库策略

### ADB

- 原始 XML 保存在 `data/raw/adb`；
- 不修改 XML；
- 解析结果先进入 `staging`；
- 事件、分类、传记字段保留 `source_record_id`；
- 对受限 `research_data` 只做本地研究使用；
- 发布分析结果时只发布聚合统计、代码和可重新下载的 ID/字段说明。

### CBDB

- 保留官方 SQLite 原库，作为只读 source-native 数据库；
- 不直接改写 CBDB 表结构；
- 通过导入脚本抽取 `BIOG_MAIN`、出生/死亡年份、地址、任官、关系和事件；
- 规范化数据进入项目自己的 `numerology.db`；
- CBDB 版本号和 SHA-256 写入 `source_snapshots`；
- 按官方许可保留来源和版本信息。当前下载页注明学术分支数据采用 CC BY-NC-SA 4.0。[CBDB 下载页](https://cbdb.hsites.harvard.edu/download-cbdb-standalone-database)

### Wikidata

- 按固定快照日期保存 SPARQL 批次 JSONL；
- 原始结果不可覆盖，只新增新快照目录；
- 导入时保留 Wikidata Q-ID、属性来源和日期精度；
- 后续如需要全量 dump，单独放入 `raw/wikidata`，不能覆盖 SPARQL 快照。

Wikidata 的结构化数据以 CC0 提供，适合作为可公开复现的独立对照源。[Wikidata Licensing](https://www.wikidata.org/wiki/Wikidata%3ALicensing)

## 推荐执行顺序

1. CBDB 原始库和第一批人物事实已导入；下一步补充任官、地址、关系和事件导入。
2. 用 ADB C sample 验证 XML 解析器和分类/事件字段处理。
3. 修复现有 ADB 全量库的分类补采和死亡日期回填，但不重新覆盖原始表。
4. 按 1900—1950、1950—2000 等时间段分批抽取 Wikidata，先做 1 个月小样本验证。
5. 三个来源分别生成质量报告后，再做人物实体对齐；对齐结果单独放 `person_links`，不改写原始记录。

## 当前结论

当前最合理的优先级是：

```text
CBDB 原始库
  + ADB C sample
  + 现有 ADB 本地库
  → 统一快照与导入规范
  → 再做 Wikidata 分批下载
  → 最后做跨源人物对齐
```

这样既能尽快获得中国历史人物样本，也不会把 ADB 的版权限制、Wikidata 的大规模抓取和 CBDB 的复杂 schema 混在一次导入中。
