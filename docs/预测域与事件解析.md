# 预测域与事件解析

更新日期：2026-07-31

## 1. 为什么要先标准化预测域

命理研究不能直接拿“命好”“富贵”“婚姻顺利”作因变量。它们既没有统一边界，也容易把命理解释反向写入结果。工程上应先把结果定义成来源中可观察、可回查、可重复计数的终点，再让不同流派的八字特征去解释这些终点。

这里的“预测域”是统计结果的分类，不是已经证明的命理能力。当前定义位于 `numerology/analysis/prediction_domains.json`，规则由 `prediction_domains.py` 解释执行。

## 3. 具体事件解析

### 3.1 ADB 结构化事件

ADB 事件先经过：

```text
event_code → event_type/event_subtype → date_start/date_end → biography_facts → prediction domain
```

例如：

```text
Relationship : Marriage
→ event_type=Relationship
→ event_subtype=Marriage
→ marriage 域
```

```text
Financial : Bankruptcy
→ event_type=Financial
→ event_subtype=Bankruptcy
→ wealth_finance 域
```

只有年份的事件保留为全年区间，例如 `2000-00-00` 变成 `2000-01-01` 至 `2000-12-31`，不能伪造为 1 月 1 日。`date_precision=9/10/11` 分别表示年/月/日。

### 3.2 CBDB 结构化事实

CBDB 目前主要提供无精确时刻的历史人物事实：

- `entry`：科举、进士、举人等入仕结果；
- `status`：官职、文武身份和宗教身份；
- `address`：籍贯等地点背景；
- `relation`：父、母、子、妻、兄弟等亲属关系。

CBDB 的“籍贯”只进入迁移/居住域的背景资料，不能自动等于迁移事件；亲属关系是关系事实，也不能自动推导亲属死亡日期。这个区分避免把静态事实误算成带时间的事件。

## 4. 三类结果不能混为一谈

1. **二元结果**：例如是否出现宗教身份证据。它仍然是“记录中出现”，不是现实世界“确实没有”。
2. **事件时间**：例如死亡或首次婚姻。可使用生存分析、区间删失或时间窗模型；日期只有年份时应按区间处理。
3. **重复事件**：例如工作变动、健康事件和关系变化。应使用事件次数、首次时间或 recurrent-event 模型，不能只压成一个模糊标签。

最重要的质量规则是：ADB 和 CBDB 都不是完整人生档案，未记录婚姻、疾病或职业变化不能记作 `negative`。当前程序只写入 `positive` 观察结果，后续若建立明确的观察窗口、完整档案子样本或在世截点，才允许生成 `unknown` / `censored` 的分母。

## 5. 如何用于命理检验

每个假设应写成：

```text
古籍命题 → 八字特征的操作化 → 预测域终点 → 纳入/排除条件 → 统计模型 → 稳健性检验
```

例如“食神主寿”不能直接检验“食神的人更长寿”，而应预先固定：出生日期质量、死亡日期最低精度、年龄截断、ADB Rodden 分层、时代/性别/来源协变量、删失定义，以及与出生月或太阳星座基线的比较。若只使用有死亡记录的人，会引入选择偏差，必须明确这是事件样本而不是全体人物。

## 6. 运行与查看

```bash
python3 standardize_prediction_domains.py
pytest -q tests
```

网页：

- `/domains`：查看各预测域的规则、观察人物数、证据数和有日期数；
- `/person/<id>`：查看单个人物命中的预测域和证据汇总；
- `/quality`：查看日期、出生资料和来源映射质量标签。

页面中的“观察人物数”不是发生率分母。正式分析前还需要定义完整观察窗口、抽样框和缺失机制，并按 ADB、CBDB、时代和日期精度分层。
